# 越界与冲突处理手册

## 1. 需要改别人的目录

**不要直接改。** 产出变更请求，交给负责人：

```
变更请求
目标文件：src/modules/order/service.ts
原因：user 模块需要调用订单查询接口
期望改动：新增 getOrdersByUser(userId) 导出
接口约定：入参 string，返回 Promise<Order[]>
提出人：lisi
负责人：wangwu
```

负责人实现后，提出人只改自己目录里的调用方。

## 2. 队长临时授权

适用于紧急修复、联调、负责人不在。

1. 修改 `ownership.yaml`，把目标路径临时指向队长或提出人
2. 提交 `chore(team): 临时授权 <path> 给 <id>`
3. 完成后立即改回
4. 在 `audit-log.md` 记录：

```markdown
| 2026-11-03 | zhangsan | src/modules/order/service.ts | 联调紧急修复 | a1b2c3d |
```

## 3. 两人需要改同一个文件

说明目录划分有问题，按顺序处理：

1. 优先拆分：把共用部分抽到 `src/shared/`，归队长
2. 其次改派：整个目录改给一个人，另一人只提需求
3. 最后才考虑临时授权

不要用「一人改前半段、一人改后半段」的方式切文件，必然冲突。

## 4. 公共接口 / 类型变更

- 只有队长改 `src/shared/**`
- 组员需要新接口 → 提变更请求
- 队长改完先合并，组员再 `git pull` 继续
- 接口未定前，组员可以先写自己模块的内部实现，不要猜接口

## 5. 合并冲突

目录划分正确时，冲突通常只出现在：

- lock 文件（`package-lock.json` / `pnpm-lock.yaml`）
- 根配置
- 公共类型

处理方式：

| 文件 | 谁解决 |
|---|---|
| lock 文件 | 队长，重新安装依赖生成 |
| 根配置 | 队长 |
| 公共类型 | 队长 |
| 自己目录 | 本人 |

解决后必须重新跑构建 / 测试。

## 6. 有人绕过规则

症状：提交里出现不属于该作者的文件。

处理：

1. 先确认是不是队长授权但漏记
2. 补 `audit-log.md`
3. 不是授权 → 找当事人，说明影响
4. 反复发生 → 缩小该成员目录范围，或改成更细的模块划分

不要直接 revert 别人的提交，先沟通。

## 7. AI 想「顺手」改

常见触发：

- 修 typo
- 统一代码风格
- 改 import 路径
- 重命名变量
- 补类型

一律按越界处理：**不改**，在回复里指出问题位置和建议负责人。

例外：如果改动只发生在自己目录内，可以改。

## 8. 身份识别失败

AI 无法确定当前是谁时：

1. 不要猜
2. 检查 `.team/me` 是否存在
3. 检查 `git config user.email` 是否在名册里
4. 仍失败 → 问用户：「你是 members.yaml 里的哪位成员？」

## 9. 仓库还没有 `.team/`

说明还没初始化：

1. 问用户谁是队长
2. 由队长按 `ownership-config.md` 建配置
3. 初始化前不要按本 skill 限制改动
